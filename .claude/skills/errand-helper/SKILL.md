# 办事问答（读流程攻略 + 我的办事，回答"下一步做什么"）

## 目标

回答用户关于自己正在办的某件事的具体问题：下一步该做什么、某份材料要不要交、还缺什么、
某个步骤能不能开始。回答必须建立在项目里已有的结构化数据上，不能凭常识编材料清单。

## 怎么获取信息

**优先通过本项目的 MCP 工具**（`.mcp.json` 里注册的那个 MCP server，工具定义在
`src/agent_tools/tools.py`，通过 `src/agent_tools/mcp_server.py` 暴露）读取数据，而不是自己去读
`community/guides/*.yaml` 或材料根目录下的 `tracks/*.yaml` 文件——工具返回的是核心库算好的状态
（`state`/`next_step`/`missing_parts` 这些字段本身就是答案的依据），比自己解析 YAML 更准确、更省
上下文。

可用的只读工具：
- `list_guides()` / `get_guide(guide_id)`：看有哪些流程攻略、攻略的结构。
- `list_tracks()` / `get_track(track_id)`：看用户正在办的某件事的完整状态——每条材料需求的
  `state`（`not_applicable`/`undecided`/`missing`/`stale`/`unconfirmed`/`ready`）、每个步骤是否
  `available`/`done`、`next_step` 是哪一步。
- `validate_community()`：共享区数据本身是否有问题（一般用不到，除非怀疑攻略数据有误）。

回答"下一步做什么"：看 `get_track` 返回的 `next_step`，对照 `steps` 里对应步骤的 `title`/`where`/
`requirements`。回答"要不要交 X"：看该材料对应 requirement 的 `state`——`not_applicable` 就是不用交，
`missing`/`unconfirmed`/`stale` 说明要交或要更新，并说明原因（例如"这条只在你是学生身份时需要，
你还没回答身份问题"对应 `undecided`）。

## 写操作规则（硬性约束）

以下三类操作都是"写"，会真的改动用户材料根目录下的 `tracks/*.yaml`：
- 改一个问题的回答（对应工具 `set_fact`）；
- 勾选/取消一个步骤（对应工具 `set_step_done`）；
- 确认/取消确认一条材料需求（对应工具 `confirm_match`）。

**任何写操作之前，必须先用一句话向用户复述你打算做什么改动（改哪个字段、从什么值改成什么值），
并等待用户明确同意（例如"好的""对""确认"），才能真的调用对应工具。** 用户没有明确同意、或者只是在
陈述事实（"我是在职"）而没有说"帮我记下来"之类的授权意图时，不要直接调用写工具——先复述、确认，
用户同意了再写。

## 不做的事

- **不读取材料文件本身的内容**：不打开、不解析材料根目录下的扫描件/PDF/图片文件；只用工具返回的
  结构化状态（是否已有、状态是什么）回答问题，涉及材料具体内容的问题（例如"我这张流水上写的是
  多少钱"）如实告诉用户这个 skill 不读取文件内容，需要用户自己看。
- **不提供、也不调用任何删除类操作**——本项目的 MCP 工具本来就没有暴露删除工具。
- **不整理新攻略、不改词表**：涉及"这份攻略是不是该补充某条材料"之类的建议，可以口头提出来，
  但改动 `community/guides/` 或 `community/material_types.yaml` 属于 `guide-author` 的职责。
- **不臆造清单**：某个问题在攻略数据里找不到依据时，明确告诉用户"攻略里没有写这条"，不要凭常识替
  官方要求下结论。
