# 官网填表（基本信息 → 真实官网，用户在场）

依据：`docs/SPEC-mvp.md` 第 1 条第 2 项（基本信息驱动的 Agent 填表）、`specs/003-personal-profile/spec.md`
（基本信息、写回规则）、`specs/002-guide-to-track/trials/README.md` 试验 #6（DS-160 实测教训）。

## 硬性红线（任何一步都适用）

1. **只在允许的网站上操作**：开始前读网站使用条款。条款禁止自动化的（例如 USTravelDocs），只给用户说明，不代填。
2. **验证码、登录、安全问题、签名、付款、最终提交**：一律交给用户（浏览器工具的 `ask`），不代做、不绕过。
3. **Security / Background 类法律声明题**（传染病、犯罪、移民违规……）：由用户本人逐题作答，Agent 不预填、不建议答案。
4. **写回基本信息**：只写用户亲口回答的内容；写之前逐条复述并征得同意（`update_personal_profile`、`confirm_personal_profile_none`）。本次行程专属信息不写回。
5. **出错就停**：网站报一次系统错误（例如 CEAC 的 Application Error）或出现拦截页（Cloudflare "blocked"），立即停下告诉用户，不连续重试、不换方法硬闯——反复报错会导致 IP 被封。

## 步骤

### 1. 查缺口（开始填之前）

- 调用 `get_profile_gaps()`。它按表格页面列出每个字段是 `filled` / `confirmed_none` / `not_applicable` / `missing`，不含字段值。
- 把 `missing` 的问题**一次问完**；回答"没有"的用 `confirm_personal_profile_none` 记下，有值的用 `update_personal_profile` 写回（都先复述确认）。
- 再问**本次行程**的信息（目的、日期、停留时长、在美住址、谁付钱、同行人、美国联系人）——这些不写回基本信息，只在本次对话里用。

### 2. 查矛盾（需要判断，工具做不了）

对照三处，把说法不一致的地方**一次性列给用户拍板**，不要自己挑一个：

- 基本信息内部：例如职位头衔前后不一；证件号和签证号是否混淆（控制号 ≠ 签证号）。
- 基本信息 vs 本地材料：用户同意后可以读材料根目录里的扫描件核对（例如护照签证页上的红色签证号、遗失记录的说法"丢失"还是"被盗"）。
- 字段含义：同一个概念在表格里可能拆成两题（例如护照"签发国"与"签发地所在国"）。

### 3. 逐页填

- 有页面对照表的网站先读对照表（DS-160 见 [`ceac-ds160.md`](./ceac-ds160.md)），用页面标志判断当前是哪一页、该用哪组信息；**对照表是提示，以页面实际为准**，发现不符就更新对照表。
- 浏览器工具先查站点经验（`learnings`），每页尽量一次批量填完。
- 每页填完、保存之前，把这一页填的关键内容列给用户确认。
- 多行列表（"Add Another"）不稳定时，用 `ask` 高亮按钮请用户点，Agent 填内容。

### 4. 收尾

- 停在签名 / 提交页之前，告诉用户申请编号和剩下要本人完成的部分。
- 新发现的网站规律写回站点经验（`learnings`）和对照表；值得记录的问题写进试验记录。
