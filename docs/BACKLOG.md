# Backlog（明确推迟的想法）

这些想法在讨论过程中被提出，都有价值，但**不在当前 MVP 范围内**。记在这里是为了不丢失，同时明确提醒任何协作的 Agent：看到这些想法时不要主动开始实现，除非项目主明确要求把某一项移进 `SPEC-mvp.md`。

- **按时间归档个人记录**（工资条等）。属于核心库范畴（机械的归档规则），但优先级低于把材料数据库+表单代填这条主线跑通。
- **从工作周报自动生成简历要点**。属于 Agent 层范畴（需要总结和写作判断），和材料/表单这条主线关系不大，适合作为独立的后续模块。**现状**：~~新版「办事工作台」已提供"工作笔记"页面~~（2026-09-24 工作台已删除，工作笔记页面随之移除；以下为当时的记录）曾提供"工作笔记"页面，把周报素材和简历素材作为**本浏览器草稿**（localStorage `pa-workbench-v1`）分开记录——只是记事，不做任何生成；**自动从周报生成简历要点这一 AI 能力仍未采纳、未实现**，存储格式与是否要做 AI 生成都还没定。旧的 `web/index.html` 里那个"工作经历和简历" tab 仍是空壳占位，不要看到它存在就当作已被采纳。
- **证件照管理与规格校验**（存储、按用途分类、校验是否符合某国签证的尺寸/背景要求）。存储和分类部分属于核心库；校验部分可能只需要普通图像处理，不一定需要模型判断，留给下一轮架构讨论时评估。
- **小红书材料清单自动检索**（目前这一步项目主手动完成：自己搜索后把结论整理成结构化清单喂给系统）。属于 Agent 层范畴，自动化收益不确定，先手动跑几轮再决定是否值得做。**拆分说明（2026-09-23）**：其中"用户把找到的攻略贴进来 → AI 解析成结构化流程"这一半已被采纳，见 `specs/002-guide-to-track/spec.md`；"自动去小红书搜索/抓取攻略"这一半仍是 backlog，且 002 明确不做。**读取说明（2026-09-28）**：用户自己给链接、Agent 在未登录浏览器里读的这一步已有 `xhs-reader` skill（见 `specs/002-guide-to-track/trials/README.md` 试验 #7）；"自动搜索"仍不做。
- **手机端提醒/确认联动**。例如材料快过期时提醒、在手机上确认表单字段。MVP 阶段先在桌面环境跑通闭环，移动端联动作为后续扩展。
- **GitHub 自动云同步机制的具体自动化**（例如定时自动 commit/push）。数据与代码分离的原则已经锁定（见 SPEC-mvp.md 第 3 条），但"多久同步一次、用什么机制触发"留待后续。
- **面向多用户的复用形式**——这条拆成两档，轻的那档已经在 `specs/001-visa-material-hub/` 这一轮讨论中正式采纳，不再算 backlog：
  - **（已采纳，不再是 backlog）个人自部署开源**：把这个"壳子"开源到 GitHub，让其他人各自在自己电脑上装一份、用自己的材料根目录，互不相干，每人一份独立本地实例。核心库接口参数化、不硬编码个人场景（见 SPEC-mvp.md 第 2 条），具体约束见 `.specify/memory/constitution.md`。
  - **（仍是 backlog）托管式多租户服务**：打包成一个大家共用的托管服务/开放 API，一套后端服务多个用户。这会把项目性质从"个人工具"变成"要对他人敏感数据负责的产品"，涉及认证、数据隔离、隐私合规等全新的设计维度，当前不做。
- **（已采纳，不再是 backlog）Track 模板 vs 实例**（2026-09-23）：已拆成共享的"流程攻略"（`community/guides/`）和个人的"我的办事"（材料根目录 `tracks/`），见 `specs/002-guide-to-track/spec.md`。
- **PersonalProfile 字段扩展参考 visa-form-copilot**（2026-09-23）：[huaxialucaicaizi/visa-form-copilot](https://github.com/huaxialucaicaizi/visa-form-copilot) 的 `references/profile-schema.md` 给出了一份跨美签/英签/申根/澳签复用的申请人档案结构（身份、护照、联系方式、家庭、工作、教育、出行和签证历史、拒签记录等），其中"未知一律填 null，绝不当成否"的原则值得照搬。等做 MVP 第 2 项"表单代填"时再参考。注意：该仓库没有开源许可证，只借鉴思路，不复制内容。
- **一段话生成基本信息**（2026-09-24，借鉴 auto-ds160-filler）：用户粘贴简历 / 自我介绍，Agent 提议要填的基本信息字段，逐条复述、用户同意后才写入。解决"第一次填基本信息太累"。属 Agent 层；写入仍走 `update_personal_profile` 的确认规则。未采纳。
- **兼容 Claude Code 以外的 Agent 工具**（2026-09-28）：仓库里的 skill（`.claude/skills/`）和 MCP 配置（`.mcp.json`）按 Claude Code 的约定写，浏览器步骤按 Claude in Chrome 写。有人用 Codex 等其他 Agent 时，skill 目录位置、浏览器工具名都不同。项目主决定暂时不管，等真有别的 Agent 用户时再由那个 Agent 自己适配（例如把 skill 复制到它认的目录、把浏览器步骤换成它的工具）。未采纳。
- **按人群的"常用证件包" + 首次使用引导**（2026-09-28，项目主提出）：共享词表只收大家都会用到的材料；像 I-20、I-94、美签、SSN 卡这类，只对长期在美的人是"常用证件"，放进共享词表会让别人的清单变吵。设想：①在 `community/` 里放可选的"证件包"（例如"在美留学 / 工作"），每个包是一组额外的材料类型；②第一次打开「我的资料」时有个引导，问"你长期在哪里生活、什么身份"，用户（或他自己的 Agent）选择启用哪些包，也可以自己加几种常用证件；③启用的包和自加的类型存在个人材料根目录，加载词表时和共享词表合并，参与材料匹配。待定：自加类型和共享词表撞名怎么办、别人的攻略引用了你没启用的类型怎么显示。未采纳。
- **界面 Agent 的 API key 模式**（2026-09-28）：让没装 Claude Code 的人填 Anthropic API key 使用界面里的 Agent。代价：项目要保管别人的密钥；工具调用和 skill 要自己实现；没有浏览器读取能力。第一版不做，spec 004 把调起 Agent 的代码单独放在 `src/agent_runner/cli.py`，以后只换这一层。未采纳。
- **旅游攻略**（2026-09-28，项目主提出）：同样是"杂乱帖子 → 结构化"，但内容是行程、景点、交通、预算，不是办事步骤和材料。可能需要一种新的共享内容类型，复用 spec 004 的新建流程（读帖子 → 草稿 → 预览 → 保存）。**位置已定（2026-09-29，项目主决定）**：不放在办事攻略里（结构不同、没有办事进度），单独作为侧边栏「03 旅游攻略」（`web/travel.html`），目前只是"待开发"占位页；「新建攻略」的类型里去掉了旅游攻略。数据结构和整理规则还没定，未采纳。
- **填表插件与贡献流程**（2026-09-28，项目主提出，已排进 spec 005 的分层，第一步只做通用引擎；**③浏览器插件已采纳（2026-09-29），见 spec 006**，①②仍在这里）：①网站专用对照表：在 `community/forms/<id>.yaml` 里加字段级对照，处理 DS-160 这类有特殊规矩的网站（国家代码、日期拆三格、多行列表）；可先核实并借用 [ChiChasesCheese/DS160-Form-AutoFiller](https://github.com/ChiChasesCheese/DS160-Form-AutoFiller)（MIT）记录的 CEAC 控件编号。②贡献流程：填完一页点"记下结构"，只记格子名字、标签、选项和对应字段，不记值，走"草稿 → 校验 → 发布"。③浏览器插件：侧边栏按当前页列出信息、一键复制、"填本页"按钮；从本地服务读基本信息，需要单独放行插件的来源（现在的防跨站检查会拒绝）。借鉴思路：FormFilla（填后标色、敏感字段点一下才填）、fillvisa-os（书签小工具，AGPL，只借思路不抄代码）。
- **多段行程**（2026-09-29，spec 007 讨论时记下）：一次办事去好几个国家、几段日期（例如申根多国、先去英国再去法国）。spec 007 先只支持一段行程（一个入境日期、一个住处）；等真遇到填表卡住再设计。未采纳。
