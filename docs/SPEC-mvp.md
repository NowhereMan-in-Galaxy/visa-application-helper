## 0. 前端入口定义（本轮更新，替代原先"签证唯一入口"的说法）

**原定义**：前端只有一个以"签证申请"为唯一入口的页面（`web/index.html`，材料资料库）。

**新定义**：新增 `web/workbench.html` 作为通用「办事工作台」，是新版工作入口（访问 `/workbench.html`，根路径仍为旧材料维护页）；**签证只是"办事"分类之一**（签证 / 工作 / 社保 / 银行补贴 / 其他）。旧的 `web/index.html` 及其 `app.js`/`style.css` 原样保留，作为"材料维护页面"（新增材料、上传文件、维护出行记录），从工作台的"材料库"页链接进入，旧功能不删不改。后端接口与数据文件本轮未改动。

**再次更新（2026-09-23）**：新增 `web/guides.html`（攻略库 + 我的办事，见 specs/002）作为新的主入口；`workbench.html` 暂时保留，其中 localStorage 版"新建办事"和"攻略草稿"将在 specs/002 Phase C 被 Track 取代。

按"真实 / 草稿 / 未来"划清当前能力边界，避免把演示当成已实现：

- **真实接通（只读展示）**：`GET /api/visa-applications`、`GET /api/visa-applications/{id}/materials`、`GET /api/materials`、`GET /api/personal-profile`（**只取 `travel_history`，不展示也不缓存证件号等其他字段**）。每路数据独立请求、独立错误处理，一个失败不影响其余内容；真实文本一律 `textContent` 写入防 XSS；`example-` 前缀的申请会标为"示例"。
- **本浏览器草稿**（`localStorage` 命名空间 `pa-workbench-v1`，**不写服务器、不跨设备、清除浏览数据即丢失**）：通用新建办事（名称/分类/描述/手填清单）及其清单勾选状态、攻略草稿（标题 + 来源链接 + 正文）、工作笔记（周报素材 / 简历素材）。读取解析失败会提示且不自动覆盖坏数据；写入失败会提示且不谎称已保存。**不缓存接口里的个人信息。**
- **明确未接入（未来能力）**：图片识别 / OCR、从文字或截图自动生成材料清单（无假 AI 识别，上传控件禁用并标注未接入）、材料文件的预览与下载（不虚构）、自动生成 Word/简历文件（不创建 Office 文件、不调用办公文档技能）、工作台内的表单代填。

## 1. MVP 范围（已锁定）

> **范围调整（2026-09-23）**：项目主重新定位产品为**大家共同维护的签证/办事流程攻略库**——任何人可以提交结构化的流程攻略，本地 Agent 辅助把杂乱攻略整理成这种结构，同时提供可交互检视的界面让人照着办、对上自己的材料。详见 [`../specs/002-guide-to-track/spec.md`](../specs/002-guide-to-track/spec.md)。它排在下面第 2 项"表单代填"之前实现；第 1 项材料数据库是它的基础，继续有效。
>
> 由此带来两条项目级约束（与第 3 条同等效力）：
> - **共享区 / 个人区硬边界**：`community/` 是公开、共同维护的内容，绝不能出现任何个人信息；个人的办事进度（Track）只存在材料根目录。任何代码都不能把个人区内容写进 `community/`。
> - **应用内不调用模型**：Agent 能力来自用户自己本地的 Agent（按 `specs/002-guide-to-track/prompt.md` 工作），应用本身不需要 API key，也不把任何内容发给第三方。这替代了第 2 条里"Agent 层通过可配置的 LLM API 调用"的隐含假设；表单代填的探索（第 1 条第 2 项）将来同样优先走本地 Agent。
>
> **待办（公开仓库前必须处理）**：`materials_index/records/` 目前含项目主的真实材料元数据，且已在 Git 历史里。仓库公开或接受他人贡献之前，必须把个人材料索引迁出到材料根目录，并清理历史（这是会改写历史的操作，需项目主单独确认）。

只做以下两件事，不做更多：

1. **材料数据库**：记录材料清单和每份材料的状态（已备齐 / 待补 / 即将过期 / 已过期），可以查询"某次申请需要什么材料，现在缺什么"。
2. **一个具体网站的表单代填**：以真实的澳大利亚签证申请网站为第一个目标，完成从材料数据库读取信息、自动填写表单字段、关键字段回显给项目主确认、确认后才提交的完整流程。

不在 MVP 范围内的功能见 `BACKLOG.md`，本轮不实现。

## 2. 架构边界：核心库 vs Agent 层（已锁定原则，实现细节待定）

项目分两层，边界如下：

- **核心库（纯代码，不依赖任何模型调用）**：材料记录的存储和查询、过期状态判断（日期比较）、表单字段映射的**执行**（给定已经探索好的映射配置和材料数据，机械地把值填进对应字段）。这一层要求确定性：相同输入永远得到相同输出，且要能独立于任何 Agent 环境运行、单独测试。
- **Agent 层（需要判断和探索能力，依赖模型）**：第一次遇到新网站表单时的结构探索（识别字段、决定映射关系）、任何需要理解非结构化内容的任务（例如未来可能做的材料清单检索）。Agent 层完成一次探索后，**必须把结果写成核心库能读取执行的配置**，不能让下一次同样的操作还要重新调用模型。

任何新功能加入前，先问它属于哪一层；如果分不清，先在 Agent 层做原型，观察规律后再下沉成核心库的确定性逻辑。

## 3. 数据与代码分离（已锁定，安全相关，见 AGENTS.md 第 3 条）

- 本仓库（Git 管理）只存代码、配置、结构化索引（不含真实内容的元数据，例如"某材料的类型、日期、状态"，但不含扫描件本身或其内容）。
- 真实材料文件存放的位置**必须可配置，不能硬编码在代码里**。项目主提出这一点是为了两个目的：一是他本人的真实材料应该能放在自己习惯的位置（不强制搬家），二是希望这个项目未来如果被别人用类似逻辑复用，"材料放哪"不该是写死在代码里的个人路径。具体做法：
  - 用一个配置文件（例如 `config.yaml` 或 `.env`，具体格式留给下一轮架构讨论）声明"材料根目录"指向哪里。
  - 这个根目录默认可以是项目文件夹内部的 `materials/`（已经在 `.gitignore` 里排除，不会被提交），也可以指向项目文件夹之外任意路径（例如项目主自己的个人材料归档空间）——两种都要支持，由配置决定，不由代码里的固定路径决定。
  - 材料索引记录中，指向真实文件的字段只存**相对于"材料根目录"的相对路径**，不存绝对路径、不复制文件内容进仓库——这样即使根目录换了位置，索引本身不用跟着改。

## 4. 材料记录字段（草案，待下一轮讨论确认具体存储格式）

以下字段是概念上应该有的信息，具体用什么文件格式（JSON / YAML / Markdown front matter）留给下一轮架构讨论决定：

| 字段 | 说明 | 示例（虚构数据） |
|---|---|---|
| `id` | 材料记录的唯一标识 | `bank-statement-2026-03` |
| `type` | 材料类型 | `银行流水` |
| `belongs_to` | 归属哪次申请/材料清单 | `澳大利亚签证-2026` |
| `obtained_date` | 取得/生成日期 | `2026-03-15` |
| `validity_rule` | 有效期规则（多久内视为有效） | `3 个月` |
| `status` | 当前状态，可由 `obtained_date` + `validity_rule` + 今天日期推导 | `即将过期` |
| `file_ref` | 相对于"材料根目录"（见第 3 条，根目录本身可配置）的相对路径，不存内容 | `签证/bank-statement-2026-03.pdf`（虚构路径） |

`status` 的推导逻辑属于核心库的确定性判断（第 2 条），不需要 Agent 参与。

## 5. MVP 验收标准（已锁定，供任何执行 Agent 核对是否做完）

- [ ] 能够列出"澳大利亚签证"这份材料清单，以及每项材料当前的状态（已备齐 / 待补 / 即将过期 / 已过期）。
- [ ] 至少一个真实签证网站的表单：能自动从材料数据库读取信息、填入对应字段；提交前必须把即将写入的关键字段完整展示给项目主，项目主明确确认后才真正提交；项目主拒绝确认时，不能自动重试或绕过。
- [ ] 同一个网站的表单字段映射，第一次探索后被保存为配置文件；第二次使用同一表单时，不需要重新调用模型做探索，直接复用已保存的映射。
- [ ] 仓库中不包含任何真实材料文件或真实个人信息（核对 `git log` 历史，不只是当前工作区）。
