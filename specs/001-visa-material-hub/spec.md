# Feature Specification: 材料资料库扩展 + 办签证智能清单

**Feature Branch**: `[001-visa-material-hub]`

**Created**: 2026-09-22

**Status**: Draft

**Input**: User description: "做一个小系统：资料和签证信息管理，个人全能小助手。数据库分成结构化个人信息（参考澳大利亚签证表格，需加 travel history）、护照扫描页（盖章页/visa page）、financial status（时间强相关、需要更新的文件夹，组织方式未定）、employment（营业执照、工作经历）、证件照（含日期标注）。需要一个好的 UI 展示这些数据库。核心功能：选国家和签证类型，用自然语言/图片描述所需材料，AI 生成 checklist 和 DDL，匹配已有材料，为缺失材料自动重命名/创建新文件夹和对应文件。周报和简历（LaTeX 模板）暂不在本次范围内。"

## 与已锁定 MVP 的关系

`docs/SPEC-mvp.md` 已经锁定了"材料数据库"（追踪材料清单和状态）与"一个具体网站的表单代填"两件事。本 spec 是对**材料数据库**这一条的正式扩容——把原本只有 7 个字段的通用材料记录，扩展成覆盖真实签证场景的完整资料库，并补上此前完全没有规划过的 UI 层和"AI 生成材料清单"能力。**已锁定的表单代填验收项不受本 spec 影响**，两者共享同一份材料库作为数据来源，但表单代填的实现细节不在本 spec 讨论范围内。

`docs/BACKLOG.md` 中的"周报生成简历"条目**保持搁置**，本次不纳入。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 打开资料库看清一次签证申请缺什么 (Priority: P1)

项目主准备一次签证申请（例如"澳大利亚签证-2026"），打开 UI，能看到这次申请关联的全部材料——结构化个人信息（含出行记录）、护照扫描页、财务状态快照、职业材料、证件照——每一项当前是"已备齐 / 待补 / 即将过期 / 已过期"，不需要凭记忆去翻文件夹确认。

**Why this priority**: 这是整个系统存在的理由——原始痛点就是"材料分散、状态记不清"。没有这一条，后面的 AI 清单生成也无从谈起（清单要匹配的对象就是这里的数据）。

**Independent Test**: 手工在材料库里录入一批虚构材料记录（覆盖五个类别），打开 UI，能在不查看原始文件的情况下，看到每类材料的完备度和过期状态，且状态与录入的日期/有效期规则计算结果一致。

**Acceptance Scenarios**:

1. **Given** 材料库中已有"护照盖章页""银行流水（3 个月内有效）""在职证明"三条记录，**When** 打开某次签证申请的资料页，**Then** 能看到三条记录各自的类别、日期、以及基于当前日期计算出的状态。
2. **Given** 银行流水的 `obtained_date` 距今已超过其 `validity_rule` 规定的有效期，**When** 查看该记录，**Then** 状态显示为"已过期"，且不需要人工重新判断。
3. **Given** 财务状态材料本质上是一组随时间累积的快照（而非单一文件），**When** 查看财务状态类别，**Then** 能看到按时间排列的多份快照记录，而不是被当成单一材料强行汇总成一条状态。

---

### User Story 2 - 用自然语言/图片生成新签证申请的材料清单 (Priority: P2)

项目主要申请一个新的签证（选定国家+类型，并给定这次申请的提交截止日期），把官网材料要求的文字说明贴进来，或者拍一张材料清单页的照片。系统据此生成一份结构化 checklist（每项材料是什么），并自动比对材料库里已有的记录，标出"这条已经有对应材料""这条还缺"。

**Why this priority**: 依赖 User Story 1 的材料库已经存在，但本身是可以独立验证的一层能力——给定清单描述和一个已有材料库快照，生成结果的正确性可以单独测试，不需要等 User Story 3 的自动建文件夹功能。

**Independent Test**: 给定一段虚构的签证材料要求文本（或图片），以及一个已经录好的材料库快照，运行生成流程，人工核对输出的 checklist 条目是否覆盖了输入描述里提到的材料种类，以及"已匹配/缺失"标注是否与材料库快照一致。

**Acceptance Scenarios**:

1. **Given** 一段自然语言描述"需要护照盖章页、近三个月银行流水、在职证明"，**When** 触发生成，**Then** 输出至少包含这三项的 checklist，每项标注是否在材料库中找到匹配记录。
2. **Given** 一张材料清单截图（图片输入），**When** 触发生成，**Then** 系统能提取出图片中列出的材料项，生成的 checklist 与文字输入路径产出的结构一致（同样的字段：材料描述、DDL、匹配状态）。
3. **Given** 生成的清单中某一项在材料库中没有对应记录，**When** 查看该项，**Then** 明确标注"缺失"，而不是静默忽略或误报为"已匹配"。

---

### User Story 3 - 为缺失材料自动建好文件夹和占位文件 (Priority: P3)

清单生成后，对标记为"缺失"的每一项，系统按统一命名规范在材料根目录下建好对应的文件夹/占位文件，项目主只需要把实际材料放进去，不用自己再想命名规则、防止和已有文件重名冲突。

**Why this priority**: 建立在 User Story 2 的清单之上，属于锦上添花的便利性功能——没有它，项目主依然可以手动整理，只是要自己想命名和路径，价值比前两条低，可以后置。

**Independent Test**: 给定一份包含若干"缺失"项的 checklist，运行文件夹生成，检查材料根目录下确实按命名规范建出了对应的空文件夹/占位文件，且不覆盖任何已存在的同名文件。

**Acceptance Scenarios**:

1. **Given** checklist 中有一项"缺失"材料，**When** 触发生成，**Then** 材料根目录下出现一个遵循统一命名规范的新文件夹或占位文件，命名中包含材料类型和所属签证申请。
2. **Given** 目标路径下已存在同名文件/文件夹，**When** 触发生成，**Then** 系统不覆盖已有内容，而是提示冲突，交由项目主决定。

---

### User Story 4 - 出国后自主更新护照页和出行记录 (Priority: P2)

项目主出国一趟回来，需要把新盖的护照页扫描件加进资料库，同时在 `travel_history` 里补一条这次出行的记录（国家、出入境日期），不需要手动改 YAML 文件、也不需要记住材料索引的目录结构。

**Why this priority**：这是项目主自己点名的"最烦人""核心需求"的场景——材料库如果不能被日常维护，很快就会和真实情况脱节，User Story 1 的"查看状态"价值也会跟着打折扣。优先级排在 User Story 2/3（AI 生成清单、自动建文件夹）之上，是因为那两个功能依赖材料库数据本身是新鲜的，而这个故事恰恰是让数据保持新鲜的手段。

**Independent Test**：不依赖 User Story 2/3，直接在前端表单里新增一条护照扫描记录（含上传文件）和一条 `travel_history` 条目，刷新页面后两者都应该出现在对应位置，且没有覆盖任何已有数据。

**Acceptance Scenarios**：

1. **Given** 材料库里已有若干护照扫描记录，**When** 项目主通过前端表单上传一张新的护照页扫描件并填写日期，**Then** 材料库里新增一条对应记录，原有记录不受影响，上传的文件被保存到材料根目录下，`materials_index/` 里只多出一条指向它的记录（file_ref）。
2. **Given** PersonalProfile 的 `travel_history` 里已有若干条记录，**When** 项目主通过前端表单新增一条出行记录，**Then** 这条记录被追加进 `travel_history`，不影响已有条目，写入的是材料根目录下的 PersonalProfile 文件（见 FR-011），不是 `materials_index/`。

---

### Edge Cases

- 财务状态这类"随时间持续更新"的材料，某一份快照文件被删除或替换后，历史记录要不要保留？（影响 User Story 1 的状态展示是否需要区分"当前有效快照"和"历史快照"）
- AI 从图片/文字描述提取材料要求时，如果原文本身写得含糊（例如没写清楚"近几个月流水"具体是几个月），生成的 `validity_rule` 应该怎么处理——留空、给出保守估计、还是明确标注为"AI 推测，需人工确认"？
- 同一份已有材料（例如同一张护照扫描页）如果能满足清单里的多个条目，匹配逻辑要不要允许一对多，还是必须强制一对一避免误导性的"重复达标"假象？
- 证件照材料如果同一批拍摄但用途不同（例如同时要交英国和申根签证），日期相同但归属的签证申请不同，材料库要如何避免把它们当成同一条记录处理？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持记录以下四类材料（`MaterialRecord`），并保留 `docs/SPEC-mvp.md` 第 4 条已有字段（`id`/`type`/`belongs_to`/`obtained_date`/`validity_rule`/`status`/`file_ref`）作为每条记录的基础属性；**结构化个人信息**（含 travel history）不算在这四类里，走 FR-011 描述的独立 `PersonalProfile` 机制，不经过 `MaterialRecord`：
  - 护照扫描页（区分"盖章页"与"visa page"等子类型）
  - 财务状态（本质是随时间新增的多份快照，而非单一文件——按材料用途分组存放，例如"工资流水""存款证明"各自单独建一条时间序列，组内按时间排列；每种用途各自判断"是否有近期有效快照"，互不影响）
  - 职业材料（营业执照、工作经历，需支持多段工作经历）
  - 证件照（每条记录需标注拍摄/生成日期）
- **FR-002**: 材料记录 MUST 关联到具体的签证申请（`belongs_to`，沿用已锁定字段），且一份材料理论上 SHOULD 能被多个签证申请引用而不需要重复录入（见 Edge Cases 的"一对多匹配"问题）。
- **FR-003**: 系统 MUST 提供一个 UI，能够按签证申请浏览上述四类 `MaterialRecord` 材料 + PersonalProfile，并直接看到每条记录的状态（已备齐 / 待补 / 即将过期 / 已过期），状态计算逻辑复用 `docs/SPEC-mvp.md` 第 4 条已锁定的"核心库确定性判断"，不需要模型参与；除了状态，UI MUST 让用户能看清每条材料对应的实际文件位置（`file_ref`），不只是一个抽象的状态标签。
- **FR-003a**: 系统 MUST 主动引导用户当前应该上传/更新哪些材料，而不是只被动展示状态、等用户自己发现缺口。对存在"建议更新频率"的材料类别（例如财务快照——即使还没过期，也可能因为太久没同步新的一份而需要提醒），系统 MUST 显示距离建议的下次更新还有多久；这个"建议更新频率"是独立于 `validity_rule`（有效期规则，判断过不过期）的另一个字段，两者不能混用同一套判断逻辑。
- **FR-004**: 系统 MUST 支持用户选择目标国家和签证类型、并填写本次申请的提交截止日期（DDL），作为一次新签证申请（`VisaApplication`）的起点；该 DDL 由本次申请下所有 checklist 项共享。
- **FR-005**: 系统 MUST 支持用户以自然语言文本或图片形式描述该签证所需材料。
- **FR-006**: 系统 MUST 基于用户提供的描述生成结构化 checklist，每一项包含：材料描述、以及与现有材料库的匹配状态（已匹配 / 缺失）。DDL（截止日期）是整个 `VisaApplication` 唯一的提交截止日期，由用户在创建签证申请时给定，所有 checklist 项共享同一个 DDL；单份材料自身的有效期要求（例如"银行流水须在近 3 个月内"）由已锁定的 `validity_rule` 字段承载，不与 DDL 混淆。
- **FR-007**: 系统 MUST 将生成的 checklist 中每一项与材料库中已有记录做匹配，匹配依据材料类型和所属签证申请，不能把明显不相关类别的材料误标为"已匹配"。
- **FR-008**: 对 checklist 中标记为"缺失"的每一项，系统 MUST 在材料根目录下自动创建遵循统一命名规范的空文件夹（不生成任何占位文件内容），命名信息 MUST 包含材料类型和所属签证申请，用户后续把实际材料放进对应文件夹即可。
- **FR-009**: 系统 MUST NOT 在自动创建文件夹/文件时覆盖材料根目录下已存在的同名内容；出现命名冲突时 MUST 提示用户，而不是静默覆盖或静默跳过。
- **FR-010**: 材料根目录路径 MUST 保持可配置（复用 `docs/SPEC-mvp.md` 第 3 条已锁定的原则），本 spec 新增的五类材料存储位置不能硬编码。
- **FR-011**: 本仓库范围内 MUST NOT 存储任何真实材料文件或真实个人信息（复用 `AGENTS.md` 第 3 条安全约束），结构化个人信息库的示例/测试数据 MUST 使用虚构值。`PersonalProfile` 的实际内容（姓名、出生日期、`travel_history` 等）属于"真实个人信息"，MUST 存储在材料根目录下的文件里，不能写进 `materials_index/`（仓库会追踪的部分）。`PersonalProfile` 是申请人级别的单一文档（不像其他材料按 `belongs_to` 挂在某次具体签证申请下——同一个人的出行记录本来就该被多次申请复用，不需要为每次申请单独存一份），因此不经过 `MaterialRecord`/`belongs_to` 这套按材料条目管理的机制，走独立的读写接口。
- **FR-012**（本轮新增）：系统 MUST 允许用户通过前端界面新增材料记录并上传对应文件，至少覆盖护照扫描页这一类（用户出国后补扫新的盖章页是高频操作，见 User Story 4）；上传的文件 MUST 保存到材料根目录下，`materials_index/` 里只新增一条指向它的记录，不在仓库内存文件内容本身。
- **FR-013**（本轮新增）：系统 MUST 允许用户通过前端界面查看和新增 `travel_history` 条目（出行记录），编辑结果写回 FR-011 所述的、材料根目录下的 `PersonalProfile` 文件。
- **FR-014**（本轮新增）：材料的"建议更新频率"（FR-003a）除了"每 N 天"这种滚动周期，MUST 还支持"每月固定第几天"这种日历周期（例如发薪日是每月 15 号，工资流水这类材料按发薪日提醒比按"上次更新后 N 天"更准确）；一条材料记录的这两种模式互斥，只能二选一。

### Key Entities *(include if feature involves data)*

- **PersonalProfile**：结构化个人信息，字段参考澳大利亚签证申请表（姓名、出生日期、国籍等常见字段），并包含 `travel_history`（`TravelHistoryEntry` 列表）。申请人级别的单一文档，不挂在某个具体 `VisaApplication` 下；实际内容存储在材料根目录下的文件里，不进 `materials_index/`（见 FR-011）。
- **TravelHistoryEntry**：一条出行记录，含国家、入境/离境日期、目的等字段。
- **MaterialRecord**：`docs/SPEC-mvp.md` 已锁定字段的扩展版本，新增 `category`（枚举：`personal_info` / `passport_scan` / `financial_snapshot` / `employment_doc` / `id_photo`）区分五大类，`passport_scan` 类下再区分"盖章页/visa page"等子类型；新增 `recommended_update_interval`（建议更新频率，可选字段，例如财务快照可设为"每月"），与已有的 `validity_rule`（判断过不过期）是两个独立维度，互不替代（见 FR-003a）。
- **VisaApplication**：一次具体的签证申请，含目标国家、签证类型、提交截止日期（DDL，本次申请下所有 checklist 项共享同一个值），关联一组 `MaterialRecord` 和一份 `MaterialChecklist`。
- **MaterialChecklist**：由 User Story 2 生成，属于某个 `VisaApplication`，包含若干 `ChecklistItem`。
- **ChecklistItem**：清单中的一项，含材料描述、匹配状态（已匹配时关联到具体 `MaterialRecord`，缺失时关联到 User Story 3 生成的空文件夹路径）。DDL 不在 `ChecklistItem` 上单独存储，读取所属 `VisaApplication` 的 DDL 即可。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 项目主打开 UI 后，3 次点击以内能看到任意一次签证申请下五大类材料各自的完备/缺失/过期状态，不需要打开原始文件确认。
- **SC-002**: 给定一份已有材料库快照和一段新的材料要求描述，生成的 checklist 中"已匹配"标注的准确率（人工核对）不低于 90%——即系统不会把明显不相关的材料误判为匹配。
- **SC-003**: 对 checklist 中的"缺失"项，系统自动创建对应文件夹/占位文件后，项目主不需要再手动决定命名规则或存放路径。
- **SC-004**: 自动创建文件夹/文件的过程中，对已存在的同名内容，冲突提示的触发率为 100%（不发生静默覆盖）。

## Assumptions

- 具体存储格式（JSON/YAML/Markdown）、UI 技术栈、AI 材料提取的实现方式，留给下一轮 `/speckit-plan` 讨论，本 spec 不预先决定（沿用 `docs/SPEC-mvp.md` 第 6 条已锁定的"留给下一轮架构讨论"的开放问题范围）。
- `docs/SPEC-mvp.md` 已锁定的"具体网站表单代填"验收项不在本 spec 重新定义范围内；本 spec 扩展的材料库将成为该功能未来的数据来源之一。
- 证件照的"是否符合某国签证尺寸/背景规格"校验不在本次范围（`docs/BACKLOG.md` 中已有相应条目，留待后续评估），本次只做存储、按用途分类、日期标注。
- 周报生成简历功能不在本次范围内，继续留在 `docs/BACKLOG.md`，不因本 spec 的推进而被隐性纳入。
- 材料匹配和 checklist 生成属于 `docs/SPEC-mvp.md` 第 2 条已锁定架构原则中的"Agent 层"，探索/生成的匹配结果原则上应可沉淀为可复用配置，避免每次都重新调用模型做同样的判断（具体沉淀形式留给 `/speckit-plan`）。
