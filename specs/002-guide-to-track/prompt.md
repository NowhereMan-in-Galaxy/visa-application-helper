# 攻略 → Track 抽取指令

给执行抽取的 Agent（Phase A 是 Claude Code 手动执行，Phase C 是 `src/agent/extract_track.py` 的系统提示词）。数据结构定义以 [`spec.md`](./spec.md) "数据结构"一节为准，本文件只规定**怎么抽**。

## 输入

1. 一篇或多篇攻略：文字、截图或网页内容。每篇分配一个 source id（`g1`、`g2`…）。
2. 材料类型词表：`materials_index/material_types.yaml` 的全部内容。
3. 可选：用户补充的背景（例如"我是在职员工""从上海送签"）。

## 输出

一个 YAML 文件的完整内容，且只有这个内容，满足：

- `status: draft`（AI 产出永远是草稿，由用户确认后改为 active）。
- 所有 `matched_record` 为 `null`，`match_confirmed` 为 `false`，`done` 为 `false`（匹配是代码的事，不是抽取的事）。
- 能通过 `src/core/tracks.py` 的校验（Phase A 实现后可以运行校验命令自查）。

## 抽取规则

1. **只抽攻略里写了的。** 攻略没提到的材料或步骤不要凭常识补。你认为明显遗漏的，可以写进 `uncertain`，并在对应的 `note` 里说明"攻略未提及，建议核实"。
2. **每条 requirement 和 step 都要有 `evidence`**，`quote` 是攻略原话摘录（不超过 60 字，截图来源就摘图中文字）。找不到原话支撑的条目不要输出。
3. **材料名先查词表。** `raw_name` 永远填攻略原叫法；它（忽略大小写和首尾空格后）与某个 alias 完全相同，才填对应 `material_type`，否则 `material_type: null`，并在回复正文里（YAML 之外，或 Phase C 的单独字段）列出"建议归入哪个 key 或建议新增什么 key"，由用户决定。
4. **能变成天数的时效要求才填 `freshness_days`**："一个月内开具" → 30，"15 天内" → 15，"近期" → 不填，写进 `note`。"覆盖近 6 个月"描述的是材料内容，不是开具时效，写进 `note`。
5. **多篇攻略说法不同就写 `conflicts`，不要自己挑一个。** 字段本身取任一说法并把该字段路径加入 `uncertain`。
6. **步骤粒度**：一个步骤 = 用户需要单独安排时间去做的一件事（去一趟银行、提交一次网申、等一次审核）。"准备材料"这种笼统步骤要拆开。
7. **`depends_on` 只写攻略明确说了先后的**，或者逻辑上必然有先后（例如"拿到在职证明"必须在"递交材料"之前）。
8. **不写任何个人信息**：攻略作者的名字、金额里的具体个人数字（"我存了 8 万"）不进 Track；通用要求（"建议余额 5 万以上"）可以写。
