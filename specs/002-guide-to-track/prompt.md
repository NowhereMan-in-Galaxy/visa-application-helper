# 攻略整理指令（杂乱图文 → 结构化流程攻略）

给贡献者本地的 Agent（Claude Code / Codex 等）用：把一篇或多篇杂乱的攻略整理成 `community/guides/<id>.yaml`。数据结构定义以 [`spec.md`](./spec.md) "数据结构"一节为准，本文件只规定**怎么抽**。

## 输入

1. 一篇或多篇攻略：文字、截图或网页内容。每篇分配一个 source id（`g1`、`g2`…）。
2. 材料类型词表：`community/material_types.yaml` 的全部内容（含 `normalize` 规则）。
3. 可选：用户补充的背景（例如"我是在职员工""从上海送签"）。

## 输出

一个 YAML 文件，保存为 `community/guides/<id>.yaml`，满足：

- 只含 spec "数据结构 §1"列出的字段。**不写任何个人状态**（谁的身份、做到哪一步、用了哪份材料）——那些属于个人区的 Track，攻略是给所有人用的。
- 不含任何个人信息：攻略作者的名字、贡献者自己的情况、具体的个人金额都不写。
- 能通过校验：在仓库根目录运行 `PYTHONPATH=src uv run python -m core.guides`，输出全部为 ✓、退出码为 0。有 ✗ 就按提示修改，改到通过为止。

## 抽取规则

1. **只抽攻略里写了的。** 攻略没提到的材料或步骤不要凭常识补。你认为明显遗漏的，可以写进 `uncertain`，并在对应的 `note` 里说明"攻略未提及，建议核实"。
2. **每条 requirement 和 step 都要有 `evidence`**，`quote` 是攻略原话摘录（不超过 60 字，截图来源就摘图中文字）。找不到原话支撑的条目不要输出。
3. **材料名先查词表。** `raw_name` 永远填攻略原叫法；它按词表的匹配规则（先按 `normalize` 删掉"原件""复印件"等修饰，再忽略大小写和空白后完全相等）能对上某个 alias 或标准名时，可以填对应 `material_type`，也可以留空交给程序自动推断；对不上就 `material_type: null`。校验命令会列出"词表认不出的叫法"，以它的输出为准，并在回复正文里（YAML 之外）列出"建议归入哪个 key 或建议新增什么 key"，由用户决定。
4. **能变成天数的时效要求才填 `freshness_days`**："一个月内开具" → 30，"15 天内" → 15，"近期" → 不填，写进 `note`。"覆盖近 6 个月"描述的是材料内容，不是开具时效，写进 `note`。
5. **多篇攻略说法不同就写 `conflicts`，不要自己挑一个。** 字段本身取任一说法并把该字段路径加入 `uncertain`。
6. **步骤粒度**：一个步骤 = 用户需要单独安排时间去做的一件事（去一趟银行、提交一次网申、等一次审核）。"准备材料"这种笼统步骤要拆开。
7. **`depends_on` 只写攻略明确说了先后的**，或者逻辑上必然有先后（例如"拿到在职证明"必须在"递交材料"之前）。
8. **不写任何个人信息**：攻略作者的名字、金额里的具体个人数字（"我存了 8 万"）不进 Track；通用要求（"建议余额 5 万以上"）可以写。
9. **按身份/情况分支的内容用 `facts` + `applies_if`**，不要拆成多个 Track，也不要只挑一种身份抽。`facts` 只收会改变清单的问题（身份、婚否、是否未成年…），`value` 一律 `null`；不收与清单无关的隐私（收入、年龄具体数字）。
10. **`kind`**：要自己去办或去拿的填 `obtain`；攻略说"可以自己写/可让 AI 生成"的（行程单、解释信）填 `generate`；完成某个操作后自然得到的（预约单、网申生成的申请表）填 `output`。
11. **"有就交、没有可跳过"的加分项填 `optional: true`**，不要用 `applies_if` 表达。
12. **材料之间"必须一致/必须呼应"的要求写进 `checks`**（例如"酒店日期与行程单一致"），不要塞进某一条 requirement 的 `note`。
13. **攻略注明了信息时效（"截至 2025-07"）就填 `sources[].as_of`**，只写到月份时取当月 1 日。
14. **等待类时长能变成天数的填 `duration_days`**（"通常 15 天，最长 45 天" → `{typical: 15, max: 45}`），写在对应的等待步骤上。
15. **每条 requirement 至少挂在一个 step 上。** 攻略没写这份材料什么时候、去哪弄时，建一个"准备 X"步骤，evidence 用该材料条目本身的原话。用户照着"下一步"做事，不挂在步骤上的材料会被漏掉。
16. **会同时成立的情况拆成不同的 fact**：例如"未成年"和"在校学生"可以同时为真，不能放进同一个单选 `identity`；只在另一个回答成立时才有意义的问题，用 `ask_if` 表达（例如先问"是否有人出资"，是才问"出资人是否同户口本"）。
17. **先搭阶段骨架，再填步骤。** 大多数办事都能分成"官网填表/预约 → 准备材料 → 递交 → 等结果"几段，按原始资料的实际情况写 `phases`（线上还是线下写进 `mode`），每个步骤标上 `phase`。原始资料写了"一般要多久""要提前多久"时，写进 `timeline` 和对应阶段的 `duration_days` / `estimate`；**没写就不填，不要凭常识估**。
18. **导出命名**：原始资料给了官方清单编号或要求的文件命名时，给每条 requirement 写 `export_name`（例如 `01-护照复印件`），并把攻略的 `export_pattern` 设为 `"{name}"`；没给就不写，使用默认的 `{seq:02d}-{name}`。`export_name` 里不能有 `/ \ : * ? " < > |`。
19. **官网链接**：原始资料里出现的官网 / 签证中心网址，写进对应步骤的 `links`（`kind: official`，`url` 原样照抄）；网址随申请国等回答变化时用 `applies_if`。不要凭记忆补网址。原始资料写了"怎么填表 / 怎么预约"的流程时，另外整理成 `community/forms/<id>.yaml`（流程级，`level: procedure`），再在步骤上用 `{kind: form_guide, form: <id>}` 链接过去。
20. **来源链接去掉追踪参数**：分享链接（尤其小红书）常带 `shareRedId`、`share_id`、`xsec_token`、`apptime` 等参数，可能追溯到分享者本人。`sources[].url` 只保留帖子本身的地址（例如 `https://www.xiaohongshu.com/explore/<帖子 id>`）。帖子配图含个人信息（证件、批准通知等）时不读取、不引用。
