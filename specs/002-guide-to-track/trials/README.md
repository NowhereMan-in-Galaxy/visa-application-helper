# 抽取试验记录

每次用真实攻略试跑 `../prompt.md`，就在这里记一条：输入是什么、产出在哪、暴露了什么问题、spec 因此改了什么。目的是让"数据结构够不够用"有证据，而不是凭感觉。

规则：输入含个人信息的试验，产出只放材料根目录，这里只记结论；输入是公开内容的，产出整理成共享攻略放进 `community/guides/`。

## 试验 #1：申根旅游签（2026-09-23）

- **输入**：[EndlessBlueWJL/schengen-visa-guide](https://github.com/EndlessBlueWJL/schengen-visa-guide) 的 `references/checklist.md`（MIT License，commit 780b004）。这是一份由真人整理好的高质量清单，用来当"标准答案"。
- **产出**：原为本目录下的 `schengen-visa-guide.track.yaml`；引入"攻略 / 我的办事"拆分后，去掉个人状态字段、转成第一份共享攻略 [`community/guides/schengen-tourist.yaml`](../../../community/guides/schengen-tourist.yaml)。29 条需求、17 个步骤、5 条一致性检查、5 个 fact。
- **执行者**：Claude Code（Opus 5.5）按 prompt.md 手动抽取，随后用一段临时校验脚本检查 spec 的全部规则。所有 evidence 原话都能在原文中逐字找到。

### 和原项目对比

| 原项目的内容 | Track 里是否保留 | 说明 |
|---|---|---|
| 18 项编号材料 + 未成年人 3 项 + 出资人/收入说明 | ✅ 全部保留 | 按身份分支用 `facts` + `applies_if` 表达 |
| 加分项（房产证、旧护照） | ✅ | `optional: true` |
| 行程单、解释信"可以 AI 生成" | ✅ | `kind: generate` |
| 预约单、申请表是操作的产物 | ✅ | `kind: output` |
| 酒店/机票/保险须与行程单一致等 | ✅ | 5 条 `checks` |
| 递签后 15～45 天出签 | ✅ | `duration_days`，将来用于倒排时间 |
| 信息截至 2025-07 | ✅ | `sources[].as_of` |
| 预算公式（按天数算余额） | ⚠️ 只能写进 `note` | 结构里没有"公式"，见下方问题 4 |
| 各国预约网址（在 SKILL.md / country-notes.md 里） | ❌ 本次输入没包含 | 且 `where` 无法随"申请国"变化，见问题 5 |
| 最终核对里的"姓名与护照一致""不用订书钉" | ❌ 本次输入没包含 | 这些写在原项目的 SKILL.md 里，不在 checklist.md |
| "一次只处理一类材料"的引导节奏 | —— | 这是界面交互，不属于数据；Phase B 前端用"下一步"实现 |

### 暴露的问题和处理

1. **有 7 条材料没挂在任何步骤上**（未成年人公证、出资人材料、退休证、房产证等）。原攻略的流程图只写了主线，没写这些材料什么时候办。
   → **已改 spec**：新增规则"每条 requirement 至少挂在一个 step 上"；prompt 新增第 15 条，要求攻略没写时补一个"准备 X"步骤。
2. **有些问题只在另一个回答成立时才有意义**（"出资人是否同户口本"只在"有人出资"时才需要问）。
   → **已改 spec**：`facts` 新增 `ask_if`，并定义了它不满足时的判定规则。
3. **"未成年"和"学生"可以同时成立**，放进同一个单选的"身份"里就表达不了。
   → **已改 prompt**（第 16 条）：会同时成立的情况拆成不同的 fact。
4. **29 条需求里有 19 条的叫法词表认不出**，例如"身份证原件 + 复印件""近 6 个月工资流水""户口本整本复印件"。词表规定"完全相等才算命中"，而攻略总爱在材料名上加"原件 + 复印件""近 N 个月""整本"这类修饰。按现在的设计，这 19 条都要由 AI 给建议、用户逐条确认，第一次使用时负担太重。
   → **已决定（2026-09-23）**：采用 A（`community/material_types.yaml` 里的 `normalize` 规则），实现后 19 条降到 1 条，剩下那条手动归类；B 随本地 Agent 能力做。当时的候选方案：
   - A. 在词表里加一组确定性的"去修饰规则"（去掉"原件""复印件""+""×N 份""近 N 个月"等），先规范化再精确匹配。估计能解决大半，但规则本身需要维护。
   - B. 维持精确匹配，但把用户确认做成**一次性批量确认**（一屏列出 19 条 AI 建议，全部同意只需点一下）。每确认一条就往词表写一条别名，词表会越用越准。
   - 倾向 **A + B 一起做**：A 减少需要确认的数量，B 让剩下的确认不再烦人。在 Phase A 实现词表查找时再定。
5. **`where` 无法随申请国变化**：法国走 TLScontact，意大利走 VFS。现在只能写成"TLScontact / VFS / BLS"这样的笼统描述。
   → **暂不改**。先观察非签证类攻略里这种情况多不多；可能的做法是给 `where` 也加 `applies_if` 变体。
6. **公式类知识**（预算 = 天数 × 单价）只能写进 `note`。
   → **暂不改**，记为以后的想法：如果常见，可以加一个"计算器"字段，由确定性代码计算。

### 本次试验带来的 spec 改动

`ask_if`、"每条需求必须挂在步骤上"的规则、prompt 第 15～16 条。问题 4 进入 spec 的待决事项。

  - g2：项目主粘贴的**小红书 AI 搜索总结**（概括 27 篇帖子）——二手资料。
- **产出**：[`community/guides/australia-visitor-600-business.yaml`](../../../community/guides/australia-visitor-600-business.yaml)（16 条需求、16 个步骤、4 个阶段、4 条核对项）和流程级填表指南 [`community/forms/immiaccount-600.yaml`](../../../community/forms/immiaccount-600.yaml)。校验全部通过；两份文件里所有 evidence 原话都能在原文中逐字找到。
- **执行者**：Claude Code（Opus 5.5）按 `guide-author` skill 执行。

### 怎么拿到帖子内容

- 在项目主的 Chrome 里打开分享链接：**弹出登录框，但关掉弹窗后正文完整显示在页面里**，不登录也能读到全文（10 项材料清单、官网地址、注意事项都在正文里）。
- 帖子只有 1 张配图，是作者的签证批准通知，上面有姓名、出生日期等个人信息；正文已经包含全部干货，所以**刻意没有读图**。结论：图片要不要读，要先看图里是什么，含个人信息的一律不读。
- 分享链接里带 `shareRedId`、`share_id`、`xsec_token` 等参数，可能追溯到分享者；攻略里只保留去掉参数的帖子地址 → 已在 `prompt.md` 补充规则（第 20 条）。
- 没有浏览器工具的 Agent：退回"复制正文 / 粘贴小红书 AI 总结"，这次 g2 就是这样来的。

### 两份资料怎么配合

- g1 是主干（材料清单、网申流程、上传技巧），g2 补充了 g1 没写的：证件照、护照有效期、翻译件、第一次申请可能要采集指纹，以及"派遣函和邀请函要对得上"这类核对项。
- 只有 g2 支持的条目都放进了 `uncertain`，界面上会提示"建议核实"。
- **想法（待定）**：来源可以标一个"可信度 / 类型"（官网、亲身经历、二手总结），界面上区别显示。先记进 backlog。

### 暴露的问题

1. **词表缺 6 种商务签材料**：form54、个人所得税纳税记录、邀请函、商务活动证明、航班行程单、翻译件。按 skill 规则没有自行修改词表，列给项目主确认后**只加了「个人所得税纳税记录」**——其余是某一次办事专用的材料，不是跨事项通用的长期材料，不进词表。由此引出新问题：一次办事里上传的专用材料该不该进长期材料库（待讨论）。
2. **导出命名**：原帖要求"文件名按系统自带的名字照抄"，也就是 ImmiAccount 里每类材料的名字；这些名字只有实际走一遍官网才知道 → 归入"字段级填表指南"（路线图第 4 项）。
3. **材料复用得到验证**：这份攻略一建好，就自动对上了材料库里已有的 6 份材料（证件类和财务类）。

## 试验 #3：杭州应届生补贴——第一份"时间提醒型"攻略（2026-09-23）

- **输入**：
  - g1：小红书帖子「一次性说清楚杭州应届生补贴」（2026-08-20）。正文只有话题标签，干货全在**一张汇总图**里；图里没有个人信息，所以读了图。
  - g2：项目主粘贴的小红书 AI 搜索总结（概括 22 篇帖子）。
- **产出**：[`community/guides/hangzhou-graduate-subsidies.yaml`](../../../community/guides/hangzhou-graduate-subsidies.yaml)：**0 条材料**、8 个步骤、2 个阶段、3 条核对项、1 处说法冲突、6 条待核实。
- **执行者**：Claude Code（Opus 5.5）按 `guide-author` skill 执行。

### 为什么要改数据结构

这类事几乎不用准备材料，难点是**记得在对的时间去办**。原有结构只有"截止日往回推"的倒排时间，没法表达"首次参保满 6 个月后才能申请、毕业 2 年后作废"这种从个人日期往后数的规则。于是新增（spec §3c）：日期类问题、步骤的可办时间窗、记录每步勾完的日期、时间提醒清单和日历导出（.ics）。

### 两份资料怎么配合

- g1 给出四项补贴的金额、时间和入口，是主干；g2 补充了"人才码认定"入口、"可以换公司但不能断缴"、租房补贴和公租房补贴互斥、法人不能申请就业补贴等避坑点（放进核对项）。
- 冲突：就业补贴在浙里办里搜什么词，两边说法不同 → `conflicts`。
- g2 里有网页残留的不可见占位符（`￼`），摘原话时避开了这些句子。

### 暴露的问题

1. **原文的时间规则常常不完整**："连续缴满 6 个月"之后多久能提交、"每年发一次"从哪天算、租房补贴 3 年里要不要每年重新确认，都没写。按"不推算"规则，只在必须给出日期的地方用最直接的解读（参保日 + 6 个月、上次领取 + 12 个月），并全部写进 `uncertain`。
2. **"毕业 1 年内首次参保"其实是资格条件**，不是一个要办的动作。现在写成"首次参保"步骤的截止时间，效果可以接受，但更准确的表达（"条件不满足 → 这项补贴不适用"）需要日期比较条件，暂不做。
3. **官网链接缺失**：两份资料都只写了 APP 名称，没有网址，所以这份攻略没有官网链接。
4. **适合真实使用**：按一组毕业、入职日期在隔离环境里试算，四项补贴各自什么时候可以申请、什么时候截止都能算出来。

## 试验 #4：美国 F-1 学生签证——第一次让 Agent 读图（OCR）（2026-09-23）

- **输入**：
  - g1：小红书笔记「LLM｜F-1美签材料checklist」（2026-06-12 编辑）。正文只有三个网址（DS-160、SEVIS 缴费、面谈预约），**24 项材料清单全在 5 张配图里**。
  - g2：项目主粘贴的小红书 AI 搜索总结（二手资料，含网页残留的 `￼` 占位符）。
  - g3–g9：7 个美国官方页面（FMJFEE.com、ICE、CEAC、USTravelDocs 三页、美国驻华使馆），用浏览器实际打开核实。
- **产出**：[`community/guides/us-f1-student.yaml`](../../../community/guides/us-f1-student.yaml)（4 个阶段、24 个步骤、32 条需求、8 个 fact、6 条核对项、3 处冲突、9 条待核实）和流程级填表指南 [`community/forms/us-f1-visa.yaml`](../../../community/forms/us-f1-visa.yaml)（缴 SEVIS 费 → 填 DS-160 → 预约面签）。校验全部通过；用脚本逐条比对，119 条 evidence 原话都能在原文（g1 按 OCR 转写稿）里逐字找到，都不超过 60 字，也没有带 `￼`。
- **执行者**：Claude Code（Opus 5.5）按 `guide-author` skill 执行。

### 怎么拿到内容（重点：读图）

1. 在项目主的 Chrome 后台标签页打开分享链接，跳转到 `/explore/<笔记 id>`；不登录，正文和配图地址都在 DOM 里（`#detail-title`、`#detail-desc`、`.swiper-slide img`）。
2. 轮播有 7 个 slide，但其中 2 个是 swiper 为循环播放复制的（带 `duplicate` 类），**实际 5 张图**。按 `data-swiper-slide-index` 排好顺序，取出 `xhscdn.com` 地址。
3. 用 `curl`（带 `User-Agent` 和 `Referer: https://www.xiaohongshu.com/`）下载 webp，`sips` 转 png，再让模型直接"看"图。
4. **先看一眼图里是什么再决定读不读**：5 张都是清单文字（标题 + Package 1–4），没有证件、I-20 或签证页，所以全部读取。
5. **识别质量**：5 张图全部读出，中文、英文、网址、数字（350 美金、185 美金、51 x 51 mm、240kb、90-100 万）都准确，没有发现错字；层级结构（Package → 编号 → 圆点）也能还原。原因是图是手机备忘录式截图，字大、背景干净。手写、拍照倾斜或表格图的效果还没试过。
6. **问题**：
   - 图里的网址和正文里的网址重复，但**旧预约网址 `cgifederal.secure.force.com` 已经失效**（域名解析不到）。按 spec"链接核实"，改用使馆官网现在指向的 USTravelDocs 预约说明页，evidence 留原帖原话，并写进 `uncertain`。
   - OCR 出来的文字没有"原文"可以复制，evidence 的"逐字比对"只能对照 Agent 自己的转写稿。转写稿存在 scratchpad，没有进仓库；以后要复核，还得重新看图。

### 官网核实

- 打开并核实：FMJFEE.com（I-901 缴费）、ICE I-901 费用页（F/M 类 350 美元，和 g1、g2 一致）、CEAC DS-160（Cloudflare 验证自动放行，官网说约 90 分钟）、USTravelDocs 中国（F 类签证费 185 美元，和 g1 一致；社交媒体须设为公开；2026-08-01 起领护照要提前预约）、美国驻华使馆非移民签证页。
- 没能核实：预约系统登录页 `usvisascheduling.com` 一直停在 Cloudflare"正在等待响应"，没有代点，放弃，所以攻略里没挂这个链接。
- 官网还带来一处**冲突**：g2 说拿到签证后要更新 EVUS，使馆官网说 EVUS 针对 10 年期 B1/B2 签证 → 写进 `conflicts`，步骤改成"核实是否需要登记 EVUS"。

### 两份资料怎么配合

- g1 是主干：完整的 24 项材料和每项的细节（份数、抬头纸、谁名下、冻结到几月）；g2 补了流程顺序（先缴 SEVIS 再填 DS-160，拿到 AA 码再预约）、面签现场流程、面签技巧和签证后的事。
- g2 的"核心 / 辅助"分法和 g1 不完全一样。`optional` 主要按 g1 原文有没有"如有 / 可取舍 / 可提供"来判断；唯一例外是房产证：g1 没写"如有"，但 g2 把它列为辅助材料、而且不是人人都有，所以设成 `optional: true` 并在 `note` 里写明。
- 冲突 3 处：存款金额（g1 按博主项目 90–100 万，g2 约 5–7 万美元）、身份证（g1 只说北京 / 沈阳要带，g2 说所有领馆都要刷）、EVUS。

### 暴露的问题

1. **词表缺 F-1 专用材料**：32 条里 18 条认不出（I-20、DS-160 确认页、SEVIS 收据、录取通知书、存款证明、资金支持函、父母收入证明、简历、语言成绩单……）。按 skill 没改词表，建议清单交给项目主决定。
2. **"父母的材料"和"本人的材料"用的是同一套词表**：父母的在职 / 收入证明如果被归到 `employment_letter`，会自动匹配到申请人**自己**的在职证明，这是错的。这次都留成 `null`。可能需要在词表里区分"谁的材料"（或者给出资人材料单独的 key），待讨论。
3. **一个 fact 表达不了"或"**：g1 说"父母和 / 或爱人的收入证明"，`applies_if` 只能"全部满足"，只好挂在"父母在职"上，爱人的写进 `note`。
4. **同一份材料在清单里自相矛盾**：导师介绍标题写"必须"，下面又说"可按专业取舍"。只能取一种（`optional: true`）并写进 `uncertain`。
5. **博主的清单编号不是官方编号**，所以没写 `export_name`（规则 18 只针对官方编号）。

## 试验 #5：美国 B1/B2——只用官方页面、由 Agent 自己找来源（2026-09-24）

- **输入**：没有用户粘贴的攻略。Agent 在项目主的 Chrome 里打开 USTravelDocs 中国（美国国务院授权的官方预约网站）的 5 个公开页面：B1/B2 签证说明、免面谈和续签、DS-160 填写指南、签证类型与费用、首页重要通知；另沿用试验 #4 已核实的预约页、CEAC、EVUS 链接。
- **产出**：[`community/guides/us-b1b2-visitor.yaml`](../../../community/guides/us-b1b2-visitor.yaml)（4 个阶段、18 个步骤、26 条需求、4 个 fact、4 条核对项、0 处冲突、3 条待核实）。校验通过。
- **执行者**：Claude Code（Opus 5.5）按 `guide-author` skill 执行；这是填表回路（路线图第 4 项）的前置。

### 观察

1. **官方来源结构清楚但"经验"少**：官方页面给了必备材料、按身份 / 目的分的支持性文件、免面谈条件，但没有准备周期、面签技巧、存款金额这类经验。按规则不补，`timeline` 写进 `uncertain`。和试验 #4 相比，官方来源几乎没有冲突，但覆盖面窄——"官方 + 经验帖"组合可能才是最好的输入。
2. **travel.state.gov 被 Cloudflare 封禁**（"Sorry, you have been blocked"），不是人机验证，等不过去。改用 USTravelDocs 中文页面，内容基本等价。
3. **USTravelDocs 使用条款禁止自动化工具**（首页原话见攻略 g5）。这决定了缴费、预约、免面谈问卷只能由用户手动操作，已写进 `docs/SPEC-mvp.md` 第 1 条第 2 项。
4. **免面谈续签是一条完整的分支**（不预约面谈、递交到合作机构网点、处理数周），用 `waiver_eligible` 一个 fact 挂在 5 个步骤 / 材料上，表达得了。
5. **词表缺口**：17 条认不出，其中几条明显能归入已有 key（纳税单、工资单、就职证明、银行月结单），建议清单交给项目主决定。
6. **"犯罪 / 法庭记录"没有做成 fact**：它会改变清单，但属于最高敏感度的信息（spec 003"不收什么"），不让用户在 Track 里回答，改成 `optional` + `note` 说明适用范围。

## 试验 #6：DS-160（B1/B2）真实填表回路——只填不交（2026-09-24）

- **目的**：验证"基本信息驱动的 Agent 填表"（`docs/SPEC-mvp.md` 第 1 条第 2 项）：Agent 读「基本信息」在真实 CEAC 官网填 DS-160，缺的问用户、确认后写回；签名 / 提交之前停下。
- **执行者**：Claude Code（Opus 5.5），浏览器用项目主自己的 Chrome；验证码、安全问题由项目主手动完成。本次行程信息用虚构假设（不写进基本信息）。
- **结果**：前 5 页（Personal 1–2、Travel、Travel Companions、Previous U.S. Travel）填完并保存；第 6 页 Address and Phone 三次保存都触发 Application Error，随后本机出口 IP 被 CEAC 的 Cloudflare 封禁，按规则停止。草稿未提交。

### 回路本身：可行

- 纸面演练时 61 个 DS-160 相关字段已填 43 个；实际填表中又问了约 20 个问题，大多数是"没有 / 否"。
- 写回基本信息的有三类：用户直接告诉的值（如证件号码类字段）、**从本地材料扫描件读出并经用户同意的值**（基本信息里有一个号码记错了种类，读扫描件核对后改正）、字段含义纠正（护照"签发国"和"签发地所在国"是两道题）。
- 发现数据质量问题：同一件事在基本信息和材料标注里说法不一致，由用户拍板。

### 暴露的问题

1. **"确认没有"存不下来** → 已修：基本信息新增 `confirmed_none`（specs/003「空值的含义」）和 MCP 工具 `confirm_personal_profile_none`。
2. **网站交互是主要成本**：约 6 页用了 150+ 次浏览器操作，大部分花在 ASP.NET 表单的刷新机制上（子字段要等下一次保存才出现、"Add Another" 只认真实点击、下拉框自带刷新）。找信息本身很快。
3. **多行列表页不稳定**：Address and Phone 页共报错 4 次，每次都要用户回答安全问题找回。封禁解除后的对照试验找到两个原因：①"其他平台"栏填了值（选 No 后连续两次保存成功）；②用脚本触发"增加 / 删除一行"（一次脚本添加邮箱行后立即报错）。真实鼠标点击这些按钮又常被悬停提示框挡住。
4. **反复报错会被封 IP**：连续三次 Application Error 后，下一次访问即被 Cloudflare 拦截；同一出口 IP 此前访问 travel.state.gov 也被拦过。
5. **工具细节**：`ask` 的完成条件不能用页面上本来就有的文字（说明页就含 "Application ID"），要用 URL；"保存 / 下一页"按钮被浏览器工具当作提交类，不能放进批处理。

### 以后的规则（已写进 `ceac.state.gov` 站点经验）

- 出现一次 Application Error 就停下交给用户，不连续重试。
- 多行列表页（地址电话、社交账号）由 Agent 给出逐项清单、用户手动填；结构简单的页由 Agent 填。
- 不用脚本直接改下拉框的值；用正常的选择动作让网站自己刷新。
