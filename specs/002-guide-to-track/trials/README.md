# 抽取试验记录

每次用真实攻略试跑 `../prompt.md`，就在这里记一条：输入是什么、产出在哪、暴露了什么问题、spec 因此改了什么。目的是让"数据结构够不够用"有证据，而不是凭感觉。

规则：输入含个人信息的试验，产出只放材料根目录，这里只记结论；输入是公开内容的，产出整理成共享攻略放进 `community/guides/`。

## 试验 #1：申根旅游签（2026-09-23）

- **输入**：[EndlessBlueWJL/schengen-visa-guide](https://github.com/EndlessBlueWJL/schengen-visa-guide) 的 `references/checklist.md`（MIT License，commit 780b004）。这是一份由真人整理好的高质量清单，用来当"标准答案"。
- **产出**：原为本目录下的 `schengen-visa-guide.track.yaml`；引入"攻略 / 我的办事"拆分后，去掉个人状态字段、转成第一份共享攻略 [`community/guides/schengen-tourist.yaml`](../../../community/guides/schengen-tourist.yaml)。29 条需求、17 个步骤、5 条一致性检查、5 个 fact。
- **执行者**：Claude Code（Opus 5.5）按 prompt.md 手动抽取，随后用一段临时校验脚本检查 spec 的全部规则。所有 evidence 原话都能在原文中逐字找到。

### 和原项目对比

| 原项目的内容 | Track 里是否保留 | 说明 |
|---|---|---|
| 18 项编号材料 + 未成年人 3 项 + 出资人/收入说明 | ✅ 全部保留 | 按身份分支用 `facts` + `applies_if` 表达 |
| 加分项（房产证、旧护照） | ✅ | `optional: true` |
| 行程单、解释信"可以 AI 生成" | ✅ | `kind: generate` |
| 预约单、申请表是操作的产物 | ✅ | `kind: output` |
| 酒店/机票/保险须与行程单一致等 | ✅ | 5 条 `checks` |
| 递签后 15～45 天出签 | ✅ | `duration_days`，将来用于倒排时间 |
| 信息截至 2025-07 | ✅ | `sources[].as_of` |
| 预算公式（按天数算余额） | ⚠️ 只能写进 `note` | 结构里没有"公式"，见下方问题 4 |
| 各国预约网址（在 SKILL.md / country-notes.md 里） | ❌ 本次输入没包含 | 且 `where` 无法随"申请国"变化，见问题 5 |
| 最终核对里的"姓名与护照一致""不用订书钉" | ❌ 本次输入没包含 | 这些写在原项目的 SKILL.md 里，不在 checklist.md |
| "一次只处理一类材料"的引导节奏 | —— | 这是界面交互，不属于数据；Phase B 前端用"下一步"实现 |

### 暴露的问题和处理

1. **有 7 条材料没挂在任何步骤上**（未成年人公证、出资人材料、退休证、房产证等）。原攻略的流程图只写了主线，没写这些材料什么时候办。
   → **已改 spec**：新增规则"每条 requirement 至少挂在一个 step 上"；prompt 新增第 15 条，要求攻略没写时补一个"准备 X"步骤。
2. **有些问题只在另一个回答成立时才有意义**（"出资人是否同户口本"只在"有人出资"时才需要问）。
   → **已改 spec**：`facts` 新增 `ask_if`，并定义了它不满足时的判定规则。
3. **"未成年"和"学生"可以同时成立**，放进同一个单选的"身份"里就表达不了。
   → **已改 prompt**（第 16 条）：会同时成立的情况拆成不同的 fact。
4. **29 条需求里有 19 条的叫法词表认不出**，例如"身份证原件 + 复印件""近 6 个月工资流水""户口本整本复印件"。词表规定"完全相等才算命中"，而攻略总爱在材料名上加"原件 + 复印件""近 N 个月""整本"这类修饰。按现在的设计，这 19 条都要由 AI 给建议、用户逐条确认，第一次使用时负担太重。
   → **已决定（2026-09-23）**：采用 A（`community/material_types.yaml` 里的 `normalize` 规则），实现后 19 条降到 1 条，剩下那条手动归类；B 随本地 Agent 能力做。当时的候选方案：
   - A. 在词表里加一组确定性的"去修饰规则"（去掉"原件""复印件""+""×N 份""近 N 个月"等），先规范化再精确匹配。估计能解决大半，但规则本身需要维护。
   - B. 维持精确匹配，但把用户确认做成**一次性批量确认**（一屏列出 19 条 AI 建议，全部同意只需点一下）。每确认一条就往词表写一条别名，词表会越用越准。
   - 倾向 **A + B 一起做**：A 减少需要确认的数量，B 让剩下的确认不再烦人。在 Phase A 实现词表查找时再定。
5. **`where` 无法随申请国变化**：法国走 TLScontact，意大利走 VFS。现在只能写成"TLScontact / VFS / BLS"这样的笼统描述。
   → **暂不改**。先观察非签证类攻略里这种情况多不多；可能的做法是给 `where` 也加 `applies_if` 变体。
6. **公式类知识**（预算 = 天数 × 单价）只能写进 `note`。
   → **暂不改**，记为以后的想法：如果常见，可以加一个"计算器"字段，由确定性代码计算。

### 本次试验带来的 spec 改动

`ask_if`、"每条需求必须挂在步骤上"的规则、prompt 第 15～16 条。问题 4 进入 spec 的待决事项。

## 试验 #2：澳洲 600 访客签证 · 商务类（2026-09-23）

- **输入**：
  - g1：小红书帖子「澳洲签证DIY下签🎉」（项目主提供分享链接）——一位申请者的亲身经历。
  - g2：项目主粘贴的**小红书 AI 搜索总结**（概括 27 篇帖子）——二手资料。
- **产出**：[`community/guides/australia-visitor-600-business.yaml`](../../../community/guides/australia-visitor-600-business.yaml)（16 条需求、16 个步骤、4 个阶段、4 条核对项）和流程级填表指南 [`community/forms/immiaccount-600.yaml`](../../../community/forms/immiaccount-600.yaml)。校验全部通过；两份文件里所有 evidence 原话都能在原文中逐字找到。
- **执行者**：Claude Code（Opus 5.5）按 `guide-author` skill 执行。

### 怎么拿到帖子内容

- 在项目主的 Chrome 里打开分享链接：**弹出登录框，但关掉弹窗后正文完整显示在页面里**，不登录也能读到全文（10 项材料清单、官网地址、注意事项都在正文里）。
- 帖子只有 1 张配图，是作者的签证批准通知，上面有姓名、出生日期等个人信息；正文已经包含全部干货，所以**刻意没有读图**。结论：图片要不要读，要先看图里是什么，含个人信息的一律不读。
- 分享链接里带 `shareRedId`、`share_id`、`xsec_token` 等参数，可能追溯到分享者；攻略里只保留去掉参数的帖子地址 → 已在 `prompt.md` 补充规则（第 20 条）。
- 没有浏览器工具的 Agent：退回"复制正文 / 粘贴小红书 AI 总结"，这次 g2 就是这样来的。

### 两份资料怎么配合

- g1 是主干（材料清单、网申流程、上传技巧），g2 补充了 g1 没写的：证件照、护照有效期、翻译件、第一次申请可能要采集指纹，以及"派遣函和邀请函要对得上"这类核对项。
- 只有 g2 支持的条目都放进了 `uncertain`，界面上会提示"建议核实"。
- **想法（待定）**：来源可以标一个"可信度 / 类型"（官网、亲身经历、二手总结），界面上区别显示。先记进 backlog。

### 暴露的问题

1. **词表缺 6 种商务签材料**：form54、个人所得税纳税记录、邀请函、商务活动证明、航班行程单、翻译件。按 skill 规则没有自行修改词表，列给项目主确认后**只加了「个人所得税纳税记录」**——其余是某一次办事专用的材料，不是跨事项通用的长期材料，不进词表。由此引出新问题：一次办事里上传的专用材料该不该进长期材料库（待讨论）。
2. **导出命名**：原帖要求"文件名按系统自带的名字照抄"，也就是 ImmiAccount 里每类材料的名字；这些名字只有实际走一遍官网才知道 → 归入"字段级填表指南"（路线图第 4 项）。
3. **材料复用得到验证**：这份攻略一建好，就自动对上了材料库里已有的 6 份材料（证件类和财务类）。

## 试验 #3：杭州应届生补贴——第一份"时间提醒型"攻略（2026-09-23）

- **输入**：
  - g1：小红书帖子「一次性说清楚杭州应届生补贴」（2026-08-20）。正文只有话题标签，干货全在**一张汇总图**里；图里没有个人信息，所以读了图。
  - g2：项目主粘贴的小红书 AI 搜索总结（概括 22 篇帖子）。
- **产出**：[`community/guides/hangzhou-graduate-subsidies.yaml`](../../../community/guides/hangzhou-graduate-subsidies.yaml)：**0 条材料**、8 个步骤、2 个阶段、3 条核对项、1 处说法冲突、6 条待核实。
- **执行者**：Claude Code（Opus 5.5）按 `guide-author` skill 执行。

### 为什么要改数据结构

这类事几乎不用准备材料，难点是**记得在对的时间去办**。原有结构只有"截止日往回推"的倒排时间，没法表达"首次参保满 6 个月后才能申请、毕业 2 年后作废"这种从个人日期往后数的规则。于是新增（spec §3c）：日期类问题、步骤的可办时间窗、记录每步勾完的日期、时间提醒清单和日历导出（.ics）。

### 两份资料怎么配合

- g1 给出四项补贴的金额、时间和入口，是主干；g2 补充了"人才码认定"入口、"可以换公司但不能断缴"、租房补贴和公租房补贴互斥、法人不能申请就业补贴等避坑点（放进核对项）。
- 冲突：就业补贴在浙里办里搜什么词，两边说法不同 → `conflicts`。
- g2 里有网页残留的不可见占位符（`￼`），摘原话时避开了这些句子。

### 暴露的问题

1. **原文的时间规则常常不完整**："连续缴满 6 个月"之后多久能提交、"每年发一次"从哪天算、租房补贴 3 年里要不要每年重新确认，都没写。按"不推算"规则，只在必须给出日期的地方用最直接的解读（参保日 + 6 个月、上次领取 + 12 个月），并全部写进 `uncertain`。
2. **"毕业 1 年内首次参保"其实是资格条件**，不是一个要办的动作。现在写成"首次参保"步骤的截止时间，效果可以接受，但更准确的表达（"条件不满足 → 这项补贴不适用"）需要日期比较条件，暂不做。
3. **官网链接缺失**：两份资料都只写了 APP 名称，没有网址，所以这份攻略没有官网链接。
4. **适合真实使用**：按一组毕业、入职日期在隔离环境里试算，四项补贴各自什么时候可以申请、什么时候截止都能算出来。
